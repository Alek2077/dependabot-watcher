# Development, release and dogfooding

This is Watcher's maintainer workflow. It separates proving a change in development from delivering that change through the same installation/update path a user receives. Use the [validation workflow](validation-workflow.md) for test procedures and the [validation record](validation.md) for historical evidence; neither a passing test nor a merged PR establishes a successful user update.

Keep distributed documentation, agent instructions and runtime defaults usable without the maintainer's private development environment. Document real Watcher prerequisites and contributor conventions, but do not require private harness files, workflow wrappers, reviewer arrangements or workstation paths. Examples and historical evidence must not become implicit user requirements; resolve operating conventions from the user's authorized configuration and repository instructions.

## Keep the environments distinct

| Environment | Purpose | Update boundary |
| --- | --- | --- |
| Development checkout and isolated test installations | Implement changes, build candidates, run diagnostics and reproduce failures | Developer-built artifacts and controlled fixtures are appropriate here. |
| Persistent dogfooding installation | Exercise acquisition, updates and ordinary maintenance with realistic settings, scheduler and history | Use the documented user installation/update procedure against an identified remote revision or published version. |

Do not replace dogfooding executables with loose development output, install a wheel from a maintainer's working directory, register an ad hoc private native build or patch saved state merely to deliver a fix. An exception requires the owner's explicit approval before the change and must be recorded as an assisted/development update, not evidence that the normal update path works. Ordinary authorization to fix code or test an isolated build is not that exception. An explicitly supplied packaged Windows prerelease following the documented channel below is not such a shortcut; record its private origin rather than claiming public package acquisition.

An agent may perform both roles, but it must keep their installations, profiles and authority separate. A user-side agent or independent session is useful for testing discoverability; a particular model, IDE or additional window is not part of the product contract.

## Development to delivery

1. Implement in the development checkout. Run proportionate deterministic, native/platform, installed-artifact and visual checks, and the applicable independent review. Use isolated test profiles; do not use the dogfooding profile as a fixture.
2. Resolve findings and verify the actual final source. Update relevant documentation and submit a focused contribution with validation evidence through the repository's contribution process.
3. Identify the merged remote commit and intended distribution channel. A merged PR is available source, not automatically a release or an updated installation.
4. Prepare the deliverable supported by that channel. Bind Python and native artifacts to their source commit/version, validate their contents and record hashes. Verify the public/user-facing acquisition instructions are usable with the tester's actual access. Missing build, authentication or distribution prerequisites are delivery blockers, not permission to substitute a local developer build.
5. Update the persistent dogfooding installation using the user procedure below. Verify installed identity, settings/history retention, native registration and scheduler behavior before continuing ordinary use.
6. Resume the user's existing workflow. Record product friction and assisted interventions accurately. Do not restart setup or erase history to turn an update/usability test into a fresh-install success.

The implementation agent owns development validation and release preparation. The agent operating the dogfooding installation follows user-facing instructions rather than private developer shortcuts. The owner provides direction, necessary access and action approvals—not repetitive development QA or manual command execution by default.

### Show frontend changes before handoff

After changing the window, personally inspect the rendered result at representative window sizes. When the owner prefers an in-app glance at completed frontend work, open or restart the updated development preview before reporting completion and leave it available for inspection; do not wait for the owner to discover that an already open window is still the old build. This is the current maintainer's stated preference, including using their actual queue, conversations and saved outcomes rather than dummy content. Use the actual development UI/backend with isolated copies of real state when possible; synthetic fixtures remain useful for edge cases but are not this maintainer's review handoff. This preference is not a requirement to show a preview to every user. If the owner is unavailable, leave a clearly identified preview available where practical and include how to find it in the handoff; respect an explicit request not to open windows. Name whether the window is a development preview or the updated installed app, and whether its data is current or a dated saved snapshot. Launch preview helpers without extra visible terminal windows. A preview must not replace the dogfooding installation, borrow its writable state, start model work or enable real repository actions merely to demonstrate appearance. Report a concrete launch blocker instead of claiming the preview was shown. Screenshots and automated checks support this handoff; they do not substitute for opening the preview when requested.

## The installation/update channel must actually exist

### Reviewed GitHub source before packaged releases

The [README installation](../README.md#install-and-set-up) and [update instructions](../README.md#update-reset-uninstall-or-roll-back) support a clean checkout of an exact reviewed GitHub tag or commit, installed by `uv` or `pipx`. “Pinned source” means selecting that exact revision, not following moving `main` and not using the active development checkout. Acquire it independently from GitHub; verify the revision and clean state before installation. Private source requires repository access; making the source public removes that prerequisite, but does not create downloadable releases or remove authentication requirements for Dependabot evidence.

Use the README's source reinstall/update instructions from that clean, pinned acquisition with the installer that owns the existing tool. This is a supported source update, not a PyPI release. The README's Python 3.14 command is an example with an explicit interpreter selection, not an instruction to silently migrate an installation using another supported interpreter. Establish the current installer and interpreter first; preserve them or obtain approval for a deliberate migration rather than assuming a reinstall preserves them automatically.

The Windows interface is a separate component. Start with the [user acquisition and selection instructions](setup.md#windows-component-for-wsl-supervision). Until a public package is available, the documented channel is an explicitly supplied private prerelease ZIP, not an agent searching for a maintainer's build. The maintainer supplies a package tied to the selected source revision using the [native packaging contract](../native/windows/README.md#package-a-verified-build); verify backend compatibility, supplied provenance and checksums, extract the complete archive into a new versioned directory, and deliberately reselect it with the intended profile and state. Record the supplied-package origin; integrity hashes alone do not authenticate the publisher. If no suitable package is supplied, report the prerequisite rather than substituting loose SDK/build-cache output. Users of a packaged component should not need the maintainer's SDK/build cache.

### Packaged releases when available

Only use the README's PyPI/versioned-package commands after the selected version is actually published. A prerelease can support dogfooding without being a stable public release, but it still needs a real, documented acquisition and update path. An unreleased source version string is not proof that a package exists.

### Versions and release notes

Use one version for Python and the Windows companion, from `src/dependabot_watcher/__init__.py`. Both artifacts belong to the same release and commit, even though users download them separately. Use `major.minor.patch`, with `aN`, `bN` or `rcN` for experimental candidates: `0.4.0a1`, then `0.4.0a2`, then `0.4.0b1` or `0.4.0rc1` when appropriate, finally `0.4.0`. Before 1.0, increment the minor number for meaningful capability batches and the patch number for smaller fixes; numbers are not decimal fractions and do not roll over at nine. Describe compatibility changes explicitly rather than promising stability solely from a version number. Never move an existing release tag or replace published artifacts with different contents; correct them in a new version.

The agent preparing a release owns assessing the changes, compatibility impact and validation evidence, then recommending the exact version and release stage with a brief rationale and any unresolved blockers. Obtain the owner's agreement to that proposal before publication unless the owner has explicitly delegated version naming for the applicable scope. Record any continuing delegation in the owner's authorized durable working context rather than relying on session memory; do not assume every owner delegates it. Delegating naming does not itself authorize tagging, publication or a visibility change, or waive release checks. The owner should not need to calculate version increments or decide technical readiness unaided.

Choose the stage from evidence, not elapsed time or a fixed number of releases. Alpha means important behavior or the supported installation/update path is still being established. Advance to beta when the intended scope is implemented and its critical safety and end-to-end user workflows have representative acceptance evidence, with remaining limitations identified. Use a release candidate when the intended stable scope is complete and only release-blocking fixes are expected. Recommend the unsuffixed version when the supported installation/update and ordinary-use paths have passed the applicable release checks, no known release-blocking safety, correctness or usability defect remains, and documented limitations are acceptable for the stated scope. Beta and release-candidate stages are optional; skip them when the evidence supports doing so. A published alpha is already a release, not a promise of stability. If substantial new scope changes the intended release, reassess the target version rather than mechanically retaining it or advancing the stage.

Keep Conventional Commit titles (`feat:`, `fix:`, `docs:`, `chore:`) and review changes normally. Version selection is deliberate, not automatically inferred from commit types. For each intended release, update the version and write `docs/release-notes/VERSION.md` in the same reviewed change. Summarize user-visible additions/improvements/fixes, update requirements and known limitations; use only the sections needed. New users learn current capabilities from README/guides; returning users and assisting agents read the selected release's notes before updating. A locally supplied `DELIVERY.md` may accompany an exceptional private package, but is not the canonical product manual or a replacement for versioned notes.

The [release workflow](../.github/workflows/release.yml) builds Python distributions and a self-contained Windows archive. Manual dispatch rehearses builds only. After validation and explicit publication approval, an annotated tag `vVERSION` must match the version exactly. Alpha/beta/release-candidate tags create a GitHub prerelease with both components, checksums and the versioned notes; they never publish to PyPI and work with a private repository when Actions is available. Stable tags publish to PyPI only for a public repository through the protected `pypi` environment, then create the GitHub release. A private stable-tag attempt does not publish; use an explicitly marked prerelease instead. No tag is automatically created on merge. Tagging, release publication and changing repository visibility remain separate authorized actions.

The simple maintainer sequence is: implement and test → review/merge the version and notes → rehearse the merged candidate → approve and push its matching annotated tag → verify both artifacts, release notes and installed update path. Do not bypass a failed release build by uploading unverified files under its tag. Ordinary development merges do not each need a release; group coherent changes into a useful version. Keep private trial packaging distinct from a successful hosted release.

Hosted build/startup failure is not a successful release. Permission to merge despite unavailable CI does not establish hosted build, package availability or release acceptance, or waive release checks.

Before package publication, maintainers must verify functioning hosted CI and a successful hosted release rehearsal for the selected candidate. This is an acceptance requirement, not an additional automatic gate enforced by the tag-triggered workflow; retain the run identity and source revision with release evidence.

When hosted CI cannot start, keep a dated explanation and revision-bound local results in the [validation record](validation.md), with a short README status link while the restriction is active. PRs should summarize the checks actually completed and disclose skipped hosted checks; commit messages describe the change rather than repeating the incident. Local checks are not a green hosted status. Preserve a representative failure or its exact diagnostic as evidence. Repeatedly deleting failed runs is not a maintenance strategy: if every push or PR creates the same known startup failure, the maintainer may deliberately suspend the affected workflow until account access changes, retain the workflow definition, and disclose the suspension. Re-enable it and verify the intended revision before claiming recovery. Remove the current README notice after recovery while retaining the dated historical record.

## Updating without losing ongoing use

Before updating, locate the actual installed command, native component selection, configuration, state and scheduler registration. Record the current and intended commit/version and check for active investigation or action work. Defer replacement of either backend or native binaries until active work has reached a verified terminal state; use supported recovery if it cannot finish normally, never kill an approved action to replace binaries. For the supported WSL/uv combination, use the [coordinated updater](setup.md#coordinated-wsluv-update-development): stage first, gracefully exit verified owners automatically, pause/restore the same task without rewriting its definition, and verify replacement before resuming. Do not make manual window closure or task removal/reinstallation routine user homework. Other paths must establish equivalent coordination or report the update as blocked rather than replacing a running installation.

Keep settings, selected targets, saved decisions, conversations, audit history and scheduler identity across updates unless a documented migration or separately approved reset requires otherwise. Never assume an older backend can read newer journals. Check compatibility before rollback and preserve state rather than silently discarding incompatible records.

After updating, verify that the command resolves to the intended installed tool rather than the development import path; version alone may be insufficient while several source revisions share a prerelease version. Verify the selected native component, saved-profile loading, queue/outcome visibility and native scheduler readback. Do not approve a new merge, invoke paid inference or synchronize a checkout merely to prove the update; those keep their own scope and consent requirements.

Continuing normal use resumes from its saved state. This does not waive applicable fresh-install or fresh-session milestone checkpoints in the validation workflow: run those separately with isolated profiles, preserving the continuing installation. Fresh acquisition, update preservation and ongoing usability are separate evidence claims; label which were exercised. Developer assistance does not erase the usefulness of later usability observations, but it must not be counted as an unassisted update.

## Storage and cleanup

Installation tools choose the supported user-level tool location; settings, durable state and the Windows component have separate platform-appropriate locations. That separation is normal, not several competing Watcher installations. Show the actual resolved paths when explaining an update, distinguishing the source checkout from the installed runtime.

Use persistent locations for a continuing dogfooding workspace and its configuration/state. Do not rely on `/tmp` surviving a restart, and do not remove a workspace retained for an ongoing user/agent trial under routine test cleanup. Temporary build/acquisition files may be disposable only when the installed product no longer depends on them and they are not the retained agent workspace. Preserve useful session continuity; do not require a reinstall simply because a disposable acquisition directory disappeared.

Keep update evidence tied to the selected revision, channel and installed result. Significant sanitized acceptance evidence belongs in the validation record; instructions belong in the workflow. Private working notes are optional and are not a prerequisite for contributing or operating Watcher.

Read the sections relevant to the task rather than loading every related document. Update active guidance in its owning section instead of appending competing instructions; cross-reference rather than repeat it elsewhere. Add historical entries for significant acceptance evidence or decisions, not routine command transcripts. Preserve valid history and distinguish it from current requirements. Improve navigation or separate material by purpose when retrieval becomes difficult, not merely to meet a word-count target.
