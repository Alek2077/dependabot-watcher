# Native integration and build-versus-integrate assessment

Last verified: 2026-10-03. Status: primary-source landscape assessment complete; owner selected continuation of the existing local CLI-first loop. Installed operating acceptance remains open.

**Implementation clarification (2026-10-18):** the optional review-channel language below records the original design direction, not a component-free supervisor capability. The current WSL supervisor requires the Windows component as its host even when the window stays hidden; the WSL review-notification route also requires it. Basic CLI operation with an existing agent or without AI is separate and does not require that component. Use [current setup requirements](setup.md#windows-component-for-wsl-supervision) when installing; component-free supervision remains future work.

## Purpose and scope

Evaluate whether Watcher should host agents and its own review interface, or supply dependency-maintenance capabilities inside tools developers already use. The first audience is individual developers and maintainers, including ChatGPT Plus users. Enterprise features are relevant constraints and future options, not prerequisites for the personal workflow.

This assessment covers the principal relevant coding-agent, GitHub and dependency-maintenance offerings. It is not a popularity survey or a claim that every vendor has been inspected. Source pages establish documented capability, not account availability, correct configuration or successful end-to-end maintenance. Recheck affected sources when a product changes; do not repeat the entire assessment without a material reason.

## Required outcome

A capable agent investigates dependencies with the right repository instructions, code, alerts, checks and user feedback; proposes and performs permitted work; refreshes evidence after actions; preserves ongoing development; and returns understandable results or requests for genuine decisions. The user should not reconstruct CLI commands or supervise ordinary command execution. Model, privacy, access and spend choices remain explicit.

Use native capabilities where they satisfy the chosen deployment's complete loop. The owner selected the existing CLI-first increment after this assessment; do not repeat broad research or add a new custom interaction/runtime layer without a concrete need. A skill is optional reusable packaging, not an agent, scheduler or enforcement boundary.

### Distinctions that change the decision

OpenAI Help explicitly separates ChatGPT tasks from Codex automations; the learn documentation presents some scheduled-work capabilities together. It also differs from Help in context/cadence wording. Therefore neither a generic task label nor a source snippet proves which tools will run in a particular account. Verify the actual chosen surface before making promises. On Windows, selecting a WSL terminal is independent from selecting a WSL agent, and Windows/WSL Codex homes do not automatically share configuration/history. Cloud repository instructions likewise do not automatically supply referenced private local harness files.

GitHub Copilot Cloud cannot approve or merge PRs, while Copilot CLI can enable native auto-merge after a repair loop. Both facts can be true. Copilot Autofix addresses code-scanning/CodeQL findings; it is not proof of comprehensive Dependabot-alert resolution. See [GitHub's security feature scope](https://docs.github.com/en/enterprise-cloud@latest/code-security/responsible-use/security-and-quality-ai-features).

Most hosted coding offerings prepare remote changes rather than silently integrate them into an actively edited personal checkout. A local capable agent can perform agreed Git integration; that is not automatically a reason to build a separate Git-management product. Native branch protections/expected-head APIs, agent access controls and instruction guidance are different layers. If an agent has direct mutation credentials, choosing Watcher's guarded executor does not technically prevent bypass through another tool. Neither host promises nor prompt-only policy should be described as enforced sole-executor authority.

## What Watcher actually adds today

The existing Python core collects Dependabot PRs and alerts across repositories, records completeness and freshness, relates alerts to remediation candidates, creates ordered evidence-backed plans and exposes them to agents. Its executor binds one permitted merge to the exact repository/base/head/action, performs live rechecks and records audit/reconciliation evidence, including ambiguous or already-applied outcomes. These are implemented domain tools, not a complete autonomous maintainer.

The development supervisor adds saved context/policy/workspace receipts, feedback/job records, owned-session continuation and a bounded app-server permission/event bridge. The native review prototype and ordinary installation/scheduled supervisor route are not yet a completed operating loop; the prototype is not a shipped package capability. Dependency-repair publication and selected local-checkout synchronization remain unimplemented. Do not advertise those gaps as advantages over native offerings.

These capabilities can be useful without being unique. GitHub already enforces branch rules and offers expected-head merge APIs; Renovate already refreshes dependent branches and combines policy with checks. A capable agent can call those directly. Watcher's incremental value must be better evidence, controlled actions, recovery or lower operational burden—not merely another scheduler, transcript, approval token or dependency dashboard.

| Responsibility | Integration preference | Evidence needed to justify custom work |
|---|---|---|
| Agent reasoning, tools and ordinary conversation | Existing capable agent host | Missing tools or unacceptable effective context/permissions in the chosen host. |
| Recurring/event execution, inbox and ordinary notices | Native host or GitHub workflow where available | A concrete eligibility, lifecycle, reliability, privacy or cost gap. |
| Update creation and routine remote merge checks | Dependabot/Renovate and GitHub controls | Maintenance outcome unsupported by their existing policies/tools. |
| Cross-repository alert/PR evidence | Evaluate Watcher's CLI as a reusable domain tool | Reliable correlation/completeness or context savings beyond agent-native collection. |
| Exact-action policy, durable audit and ambiguous recovery | Evaluate Watcher's executor/journals alongside GitHub enforcement | Clear safety/recovery benefit that a native workflow does not already provide. |
| Local working-copy integration | Agent using explicit registered paths and preservation policy | Neither a hosted clone nor current Watcher implementation establishes safe developer-work integration. |
| Custom native window and agent host | Finish the selected bounded CLI-first connection; visible window use can remain optional, while the current WSL supervisor requires the component | Verify useful operation and lifecycle where no CLI-native decision channel was established. Do not expand into a general agent platform; a tested desktop-native host can replace those responsibilities for its deployment. |

App-server remains a supported rich-client embedding interface, not an obsolete API. It is unnecessary when Codex's own client owns the interaction. Keeping a validated optional adapter is different from making every user install a Watcher-specific agent client. Likewise, future provider portability is not justification for implementing every provider now: retain plain CLI/data/action boundaries and add integrations when actual host acceptance establishes a need. See [OpenAI's embedding and SDK guidance](https://learn.chatgpt.com/docs/app-server).

## Cost and portability

OpenAI's current published personal prices are Plus $20/month and Pro $100/$200/$500 USD/month. Local and Cloud work share usage allowances; token/context/tool/model choices matter. Dots is not a Plus prerequisite. Watcher's AI path consumes the selected subscription/API budget too, so it is not free inference or inherently cheaper hosting. Deterministic changed-work detection might save inference usage, but that saving is unmeasured.

Use the existing Plus account as the first practical acceptance path, not as a product-wide requirement. Do not require buying another subscription simply to validate a competing architecture. Provider-neutral command/state contracts can accommodate another host without Watcher running that host itself; actual available adapters and tested compatibility must be distinguished from this design possibility.

## Unresolved acceptance questions

1. Can the selected native host run with the intended account, model, local/WSL harness and tools, and collect complete private alert/PR evidence without repeated user interventions?
2. Does it route meaningful approval, feedback and permission decisions visibly and continue with the correct context? Does unattended configuration instead fail silently or grant more authority than intended?
3. Does it refresh after a base/head change, refuse obsolete consent, distinguish attempted from confirmed mutations, and recover from an interrupted/uncertain action without blindly repeating it?
4. Can it preserve selected dirty/divergent local work and integrate agreed remote changes, with an understandable report? Is that needed for the user, rather than assumed for all remote-only maintainers?
5. Does adding Watcher's core materially improve the same job's completeness, context cost, safety, recoverability or human effort enough to justify its installation and maintenance?

These require a bounded real-world comparison, not more synthetic component tests or inferring success from a green session status. First compare read-only collection/investigation on the same evidence and permission scope, then test feedback/interruption and one separately authorized consequential action where appropriate. Agent owns setup, execution and evidence analysis; user input is reserved for unavailable account access, actual visual receipt and explicit authority decisions. Do not create account integrations, permanent schedules or live mutations merely because this assessment exists.

## Selected direction and remaining acceptance

The owner authorized resuming the existing CLI-first loop after clarifying the delivery contract. The research establishes substantial overlap but does not establish a universal replacement for the CLI-first scheduler and decision channel. Codex desktop can own scheduling and interaction for users who choose that host; its local app must remain running, but a specific chat need not remain open or selected. CLI and IDE do not provide the documented Scheduled management interface. A standalone CLI installation therefore still needs a trigger and a durable decision/result channel; the current WSL supervisor uses an OS scheduler and the required Windows host component, whose window can stay hidden. Component-free supervision remains future work. Do not infer their obsolescence from desktop capabilities, or require all users to adopt that desktop application.

The present recommendation for the original CLI-first MVP is local scheduled maintenance with the existing core, resumable Codex supervision and the Windows review/host component. That component is required for the current WSL supervisor; optional component installation is a future capability, distinct from keeping the window hidden today. Restrict the review channel to readable recommendations, questions, scoped permissions, exact approvals and outcomes; do not expand it into another general agent platform. Existing native interfaces are alternatives for later integrations where they demonstrably satisfy the same loop. Cloud can execute remote work, but the documented Plus offerings have not established the complete recurring coding, private-alert access, interactive authorization and selected local-checkout integration required here; do not migrate the MVP to it on that assumption. Preserve all existing code and development tools. A clear finding that a native host sufficiently replaces one deployment's custom layer remains a valid outcome.

AI-supervised maintenance is the intended recommended path, not an exception used only when deterministic triage fails. Mechanical collection, change detection and baseline ordering can remain model-free; they are not compatibility review or a reasoned merge endorsement. Pending maintenance with relevant changed evidence, user feedback, due follow-up or recovery must enter the configured supervisor path. Model-required operation must not silently downgrade on provider failure. An unchanged complete run with no due work need not consume another model call. Tool permissions, merge authority and AI-review requirements remain separate controls; these are desired policy boundaries, not claims that ordinary installed scheduling already enforces them.

Publication, personal operating readiness and eventual broad autonomy remain separate decisions. An honest useful open-source CLI need not wait for every future feature; a public CV project is not evidence that its custom background UI is justified. Existing disclosure, security, exact-commit CI and explicit publication authorization gates remain unchanged.
